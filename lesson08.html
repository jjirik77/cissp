Day 5, Morning • Domain 8

Software Development Security

Most breaches end in software, so security has to begin there. Domain 8 asks how an organization builds security into every phase of development, controls the tools and pipelines that produce code, judges software it buys rather than builds, and finds flaws while they are still cheap to fix.

Session: Day 5, 9:00 to 12:00 Duration: ~3 hrs Exam Weight: 11.2% Knowledge Check: 8 Questions

Overview

Build it in, do not bolt it on

A CISSP is not expected to write code. A CISSP is expected to make sure the people who write it have the requirements, tools, reviews, and gates that keep flaws out of production. The earlier a flaw is found, the less it costs. A design flaw caught on a whiteboard costs an hour. The same flaw found by an attacker costs a breach.

This lesson covers security across the development life cycle, the controls in a development ecosystem, how to assess whether those controls work, how to evaluate acquired software, and the coding weaknesses that matter most.

🧭 Think like a managerThe best answer usually moves security earlier: requirements and threat modeling over penetration testing, pipeline gates over emergency patches. Testing finds flaws. Good process prevents them.

Security in the Software Development Life Cycle

Every life cycle has the same broad phases: requirements, design, development, testing, deployment, operations and maintenance, and retirement. Security has a job in each one.

PhaseSecurity activity
RequirementsSecurity and privacy requirements, misuse and abuse cases, compliance needs
DesignThreat modeling, secure design principles, attack surface review
DevelopmentSecure coding standards, peer review, SAST, secrets scanning
TestingDAST, fuzzing, penetration testing, security regression tests
DeploymentHardened configuration, code signing, change approval
OperationsMonitoring, patching, vulnerability management, change management
RetirementData migration or destruction, decommissioning, removing access

Development methodologies

  • Waterfall: sequential phases with sign-off between them. Easy to audit, slow to change.
  • Spiral: repeated cycles, each with an explicit risk analysis. Good for large, high-risk projects.
  • Agile and Scrum: short sprints and working software. Security fits as user stories, a definition of done, and a security champion on each team.
  • DevOps and DevSecOps: development and operations share ownership through automation. DevSecOps adds automated security gates to the pipeline.
  • Scaled Agile Framework (SAFe): coordinates many Agile teams across a large organization.

Maturity models and governance

  • Capability Maturity Model (CMM and CMMI): five levels from initial (ad hoc) through repeatable, defined, managed, and optimizing.
  • OWASP SAMM: the Software Assurance Maturity Model, which measures and plans security practices across business functions.
  • BSIMM: a descriptive model built from observing what real organizations do.
  • Change management: every change is requested, assessed for security impact, approved, tested, and documented.
  • Integrated product team (IPT): a cross-functional team, including security, that owns a product across its life cycle.
💡 Exam TipSecurity requirements belong in the earliest phase. When asked when to involve security in a project, the answer is at initiation and requirements, not before deployment.

Shift left, the SSDF, and SBOM requirements

Shift left means moving security work earlier in the life cycle: requirements and threat modeling instead of a penetration test the week before launch. Early fixes are cheaper and change the design rather than patching around it.

The Secure Software Development Framework (SSDF), NIST SP 800-218, describes secure development as outcomes rather than tools. It groups its practices into four areas:

  • Prepare the organization (PO): roles, training, policies, and secure toolchains.
  • Protect the software (PS): protect code, builds, and releases from tampering, and keep release integrity verifiable.
  • Produce well-secured software (PW): secure design, coding, review, and testing.
  • Respond to vulnerabilities (RV): find, fix, and learn from vulnerabilities after release.

U.S. federal agencies now ask software producers to attest that they follow secure development practices drawn from the SSDF, and many buyers outside government ask the same. A software bill of materials (SBOM) is the matching transparency requirement: a machine-readable list of every component in a product, with supplier, name, version, a unique identifier, and dependency relationships. The two common formats are SPDX (an ISO/IEC standard) and CycloneDX (an OWASP project). Writing “provide an SBOM with every release” into contracts turns the requirement into something you can enforce.

2

Security Controls in Development Ecosystems

Code is only as trustworthy as the environment that produced it. The ecosystem includes programming languages, libraries, tool sets, the integrated development environment (IDE), the runtime, continuous integration and continuous delivery (CI/CD) pipelines, software configuration management, and code repositories.

  • Languages and runtimes: memory-safe languages such as Rust, Go, Java, C#, and Swift manage memory for the programmer and remove whole classes of flaws, such as buffer overflows and use-after-free errors, that C and C++ leave to the programmer. Government guidance now urges new projects to choose memory-safe languages and to publish a roadmap for older C and C++ code. Object-oriented languages add encapsulation, which helps hide internal state, but they are not automatically memory safe.
  • Libraries: approved sources only, pinned versions, and a process to update when a vulnerability is published.
  • IDE and tool sets: security linters and plugins in the IDE give feedback while code is written.
  • Code repositories: branch protection, required reviews, signed commits, and secrets scanning to stop credentials from being committed.
  • CI/CD: the pipeline is a high-value target. Protect its credentials, restrict who can change build definitions, and sign the artifacts it produces.
  • Software configuration management: versions every change so any build can be reproduced and traced.

Application security testing

MethodHow it worksStrengthLimitation
SASTAnalyzes code at restEarly; points to the exact lineFalse positives; misses runtime and configuration issues
DASTAttacks the running appNo source needed; finds runtime and configuration flawsLate; cannot point to code; limited coverage

SAST and DAST are complementary: one reads the code, the other attacks the running result. Some teams add interactive testing, an agent inside the running application that combines both views. Checking third-party components is a separate job, covered with open source in Section 5.

3

Secure Coding and Source-Code Weaknesses

Most weaknesses come from trusting input or mishandling state. The OWASP Top 10 ranks the most critical web application risks, and the Common Weakness Enumeration (CWE) catalogs weakness types by number. Both are references, not checklists.

WeaknessWhat goes wrongPrimary fix
SQL and command injectionInput is executed as codeParameterized queries; avoid shell calls; allowlist validation
Cross-site scripting (XSS)Input is rendered as script in another user’s browserContext-aware output encoding; Content Security Policy
Cross-site request forgery (CSRF)A logged-in browser is tricked into sending a requestAnti-CSRF tokens; SameSite cookies; reauthentication
Buffer overflowData written past the end of a memory bufferBounds checking; memory-safe languages; ASLR and DEP
Race condition (TOCTOU)State changes between check and useAtomic operations; locking
Insecure deserializationUntrusted data rebuilds objects that run codeDo not deserialize untrusted data; integrity checks; safe formats
Hardcoded secretsPasswords and keys in source codeSecrets manager; secrets scanning; key rotation

API security and good practice

  • APIs: authenticate every call, authorize every object (broken object-level authorization is a leading API flaw), rate limit, validate schemas, and never expose more data than the client needs.
  • Practices: validate input on the server with allowlists, encode output, fail securely, handle errors without revealing internals, use vetted cryptographic libraries, and log security events.
💡 Exam TipInput validation helps against nearly everything, but it is rarely the single best answer. For SQL injection the best answer is parameterized queries. For XSS it is output encoding.

Assessing the Effectiveness of Software Security

Controls in a pipeline are only useful if someone checks that they work. Assessment asks two questions: are changes controlled and traceable, and is the remaining risk known and accepted?

  • Auditing and logging of changes: every commit, approval, build, and deployment is logged with who, what, and when. Logs are protected from alteration so they can support investigations.
  • Risk analysis and mitigation: findings from testing are rated, assigned owners and deadlines, and tracked. Exceptions need documented risk acceptance.
  • Metrics: defect density, mean time to remediate, percentage of builds passing security gates, and open findings by severity.
  • Separation of duties: the developer who writes a change should not be the only person who approves and deploys it.
💡 Exam TipRegression testing confirms that a change did not break existing functions or reintroduce old flaws. Expect it in questions about patches and change management.
5

Security Impact of Acquired Software

Most organizations buy far more software than they build. You inherit the security of every product you install, so evaluation must happen before purchase and continue after.

SourceMain riskAssurance approach
COTSNo source access; you depend on the vendor’s practicesVendor attestations, independent testing, contract terms, patch commitments
Open sourceUnmaintained or vulnerable components, license obligationsSoftware composition analysis (SCA), SBOM, project health review, pinned versions
Third-party customQuality depends on the contractorSecure coding requirements in contract, code review, escrow
Managed servicesShared control of enterprise applicationsSLAs, SOC 2 reports, right to audit
Cloud (SaaS, PaaS, IaaS, FaaS)Shared responsibility and limited visibility; with FaaS the provider runs everything below your function codeClarify the responsibility model; review certifications; configure securely

Software composition analysis

Most of a modern application is open source code the team did not write. SCA tools read the project’s dependency files and binaries, build an inventory of every component, including the dependencies of dependencies, and match it against vulnerability databases and license terms. Run SCA in the pipeline on every build, not once a year, because new vulnerabilities are published against old components every day. SCA also produces the SBOM.

An SBOM lets an organization answer the first question after a new vulnerability is published: do we run the affected component, and where? Without one, that answer can take weeks.

Compare “Test at the end only” with “Full DevSecOps.” Late testing catches some coding and configuration flaws, but at ten times the cost, and it never sees vulnerable libraries, leaked secrets, or tampered builds. Each type of defect needs the gate built for it, and the cheapest gates sit at the left. That is the business case for shifting left, in one picture.

7

Faculty Teaching Segment

Students who are not programmers can still learn secure development. Focus on recognizing weaknesses, choosing controls, and reading tool output, not on writing exploits.

  • Signature assignment: give students five short code samples, each with one weakness. For each, they name the weakness and its CWE category, explain the impact, rewrite the vulnerable lines, and name the pipeline gate that should have caught it.
  • Rubric criteria: weakness identified correctly, root-cause fix rather than a filter, a correct gate choice, and a clear impact statement a product owner would understand.
  • Lab idea: run a free SAST tool and a free SCA tool against a small, intentionally vulnerable sample app on student machines. Students triage the findings, separate true from false positives, and read the generated SBOM.
  • Course fit: this domain fits a secure programming, web development, or DevSecOps course. It supports the CAE-CD Secure Programming Practices (SPP), Software Assurance (SAS), and Supply Chain Security (SCS) Knowledge Units.
🎓 Teaching noteAsk students to find the cheapest gate set that keeps escaped defects under ten in the pipeline model. They discover that no single tool is enough, and that each defect type needs its own control.

Scored Knowledge Check

Test your understanding

Select the best answer for each question, then submit for your score and the rationale for every item. Like the exam, several options may be true; choose the best one.

Q1.A code review finds a login form that builds its SQL statement by joining user input into the query string. What is the BEST fix?

Question 1 options
Correct: C. Parameterized queries separate code from data, which removes the root cause. A WAF and character filtering are partial, bypassable layers, and encryption does not affect injection.

Q2.What does software composition analysis (SCA) primarily identify?

Question 2 options
Correct: A. SCA inventories components, often producing an SBOM, and matches them against vulnerability and license data. It does not analyze custom logic or runtime configuration.

Q3.A college must test a purchased web application. The vendor will not provide source code. Which testing approach fits BEST?

Question 3 options
Correct: D. DAST tests the running application from the outside and needs no source. SAST, code review, and repository scanning all require access to the code.

Q4.A college that sells a scheduling app to a state agency is asked to attest that it follows secure development practices. Which framework is the agency MOST likely referring to?

Question 4 options
Correct: B. The SSDF defines the secure development practices that government buyers ask producers to attest to. The OWASP Top 10 is a list of web risks, CMM measures process maturity in general, and PCI DSS protects payment card data.

Q5.A program checks that a user may write to a file, then opens the file a moment later. An attacker swaps the file for a link to a system file in between. What is this weakness?

Question 5 options
Correct: B. The state changed between the check and the use, which defines a TOCTOU race condition. Atomic operations and locking prevent it.

Q6.A college plans to buy commercial off-the-shelf student information software. What gives the BEST assurance about its security before purchase?

Question 6 options
Correct: D. Without source access, assurance comes from independent evidence and enforceable commitments. Popularity and claims are not evidence.

Q7.In which phase is a security flaw usually LEAST expensive to fix?

Question 7 options
Correct: A. Fixing a flaw before code exists means changing a document, not rebuilding and redeploying software. Cost grows with each later phase, which is the case for shifting left.

Q8.A team is starting a new network service and wants to eliminate buffer overflow and use-after-free flaws by design. What is the BEST choice?

Question 8 options
Correct: C. Memory-safe languages prevent these memory errors by design, which is the shift-left answer. SAST and a WAF find or block some instances after the fact, and signing proves integrity, not safety.
